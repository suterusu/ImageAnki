# Usecase Description Authoring

## 概要

`docs/usecases/<ScreenName>/<ScreenName>.md` を、後続スキルが機械的に読み取れる形式で作成する。
対象は「ユーザー操作」と「システム応答」の事実のみとし、実装詳細は書かない。
1ファイルには1画面のユースケースのみを記述し、別画面の責務は別ファイルへ分離する。
記述開始前に、画面構成（画面名と責務）をユーザーと相談して合意する。
同時に `docs/usecases/<ScreenName>/penScript.md` と `docs/usecases/<ScreenName>/viewScript.md` を作成する（初期は空）。
`viewScript.md` は空のままでもよいが、後続のフロー1+を実施する前提がある場合は次のような TODO を1行入れる:
`TODO: フロー1+でナビゲーションバー要件を追記する`

## ユースケース本文の記述対象（必須）

- 本文（基本/分岐/例外）は「意図」と「結果」を書く
- 原則として「ユーザー操作1つ + それに対するシステム応答」で1ユースケースを構成する
- UI操作は本文に混ぜずファイル末尾の `## UIイベント` に記載する
- UI要素とUI状態は同一ファイル内の `## UI要素` / `## UI状態` に記載する
- ユーザー入力は、システムに渡す値の候補が一意に分かる粒度で書く
- ただし、確認アラート/確認ダイアログ上の確定・キャンセル操作は、起点となる操作と同一ユースケース内の分岐として扱う

## 画面遷移の記述ルール（必須）

- 画面遷移は `docs/ScreenFlow.md` のナビゲーションツリー（木構造）で管理する
- ユースケース本文では「システムは〜画面へ遷移する」とだけ記述する
- push / pop / popToRoot / switchTab などのナビゲーション操作はユースケースに書かない
- 具体的な遷移方法はナビゲーションツリーから一意に導出する
- 遷移先にデータを渡す場合は「システムは〜IDの〜画面へ遷移する」の形で記述する

## UI追記ルール（必須）

- 1ファイル内のユースケース記述をすべて書いた後ろに、次をこの順で置く
  - `## UI要素`
  - `## UI状態`
  - `## UIイベント`
- 各UIセクションは画面単位の一覧として記述し、ユースケース見出しで分割しなくてよい
- `## UIイベント` には、`<手順番号>「<手順文>」: <具体UI操作>` 形式で書く
- `## UI要素` には、画面内で操作/表示に関わる要素名を書く
- `## UI状態` には、画面内で変化・参照される状態名を書く
- UIイベントは1手順1つを原則とし、複数候補がある場合は「または」で明示する

## ファイル分割ルール（必須）

- `docs/usecases/<ScreenName>/<ScreenName>.md` は1ファイル1画面で作成する
- `docs/usecases/<ScreenName>/penScript.md` を同じディレクトリに作成する（初期は空）
- `docs/usecases/<ScreenName>/viewScript.md` を同じディレクトリに作成する（初期は空）
- フロー1+を続ける場合、`viewScript.md` に TODO 行を入れて未反映項目を明示してよい
- 画面遷移先の振る舞い（例: 結果確認画面の操作）は遷移先ファイルに書く
- 1つの画面内で完結しない要求は、画面ごとに複数ファイルへ分割する
- 既存ファイルに他画面のユースケースが混在している場合は分離してから更新する

## 作成手順

### 0. 画面構成を相談して合意する（必須）

- ユーザーに画面一覧案を提示し、必要画面を相談して確定する
- 各画面の責務を1〜2行で明確化する
- 合意した画面単位で `docs/usecases/<ScreenName>/<ScreenName>.md` の作成対象を確定する
- 各画面で `docs/usecases/<ScreenName>/penScript.md` と `docs/usecases/<ScreenName>/viewScript.md` も作成対象に含める
- ただし、ユーザー入力に画面一覧と各画面の責務が明示され、解釈の曖昧さがない場合は、この相談フェーズを省略して作成に進んでよい

### 1. 画面責務と基本フローを作る

- 画面名を `ScreenName` として確定する（例: `WordListScreen`）
- 対象ファイルを1画面に限定し、他画面の責務を含めない
- 画面で達成する主要目的を2〜6個のユースケースに分割する
- 分割の基準は「ユーザー操作単位」にする（例: 選択する / 入力する / 開始を要求する）
- ユースケース名は動詞で終わる短い文にする（例: 「単語を登録する」）
- ユースケース名は、原則として対応する `基本フロー1` の文と言い換えずに揃える
- 各ユースケースはまず `### 基本フロー` を書く
- 手順は時系列で `1.` から連番にする
- 手順は必ず `ユーザーは ...` / `システムは ...` で始める
- 1手順1アクションに分割する
- 1行1処理までに制限する（`AしてBする` のような複合文は禁止し、別手順へ分割する）
- 画面遷移直前の一時値は、`保持する` よりも `〜IDの〜画面へ遷移する` の形で遷移先に含めて記述する
- 画面表示時/遷移時に必要な初期処理（データ読み込み、初期化、ローディング表示）を省略しない
- 操作手段ではなく、利用者の意図とシステム結果で書く
- `ユーザーは ...` 手順に対応するUI操作を `## UIイベント` に追記する（例: `基本フロー2「...」: 判定カードを右スワイプする`）

### 2. 分岐フローと例外フローを追加する

- 条件分岐は `### 分岐フローA: ...（基本フローNから分岐）` を使う
- エラー系は `### 例外フローB: ...（基本フローNから分岐）` を使う
- 確認アラート/確認ダイアログの確定・キャンセルは、起点操作のユースケース内で分岐として記述する
- 手順番号は分岐元に紐づける（例: `3-A`, `4-A`, `3-B`）
- 分岐終端では「処理を終了する」または基本フロー復帰を明記する

### 3. ScreenFlow.md を生成・更新する

- 全画面のユースケース記述が完成した後に実施する
- `references/screenflow_template.md` のフォーマットに従い `docs/ScreenFlow.md` を生成する
- 各ユースケース記述から「システムは〜画面へ遷移する」手順を抽出し、ナビゲーションツリーを構成する
- ツリーは木構造を維持する（任意の2画面間のパスが1つだけ存在する）

### 4. 表現を正規化して仕上げ確認する

- UI/実装依存語を避け、振る舞いとして書く
- UI操作の記述は `## UIイベント` に限定し、本文は意図/結果のまま保つ
- UIイベントは発火に必要な最小限のみ記述する
- 入力値の意味は明示する（例: 正解/不正解）
- ドメインカードで英語名の概念を使う場合は、初出で `和名（英語名）` を明記し、以降は和名で統一する（例: 学習回（StudySession））
- レアケースと判断できるエラーは、原則として画面内常設表示ではなくアラートとして記述する
- 取得失敗/読み込み失敗/保存失敗などの処理失敗は、原則として「エラーアラートを表示する」と記述する
- `エラーを表示する` のような曖昧表現は避け、`エラーアラート` または `入力エラー表示` のどちらかを明示する
- 英語技術用語は必要最小限にする（`Observer`, `ローディング状態` など既存語のみ）
- 曖昧語を避ける（「いい感じに」「適切に」など）
- 画面構成の合意結果とファイル構成が一致している
- ファイルが1画面の責務だけで構成されている
- 全ユースケースが `## ユースケースN: ...` で連番になっている
- すべての手順が `ユーザーは` / `システムは` で始まる
- すべての手順が1行1処理になっている（1手順内に複数動作が混在していない）
- 画面遷移手順に不要な `保持する` が残っていない
- `ユーザーは` 手順に対応する `## UIイベント` があり、操作とイベントが対応づいている
- ファイル末尾に `## UI要素` / `## UI状態` / `## UIイベント` があり、順序が守られている
- `docs/usecases/<ScreenName>/penScript.md` が存在する（初期は空でよい）
- `docs/usecases/<ScreenName>/viewScript.md` が存在する（初期は空でよい）
- 本文だけで、システムに渡る入力値の候補が判断できる
- 例外フローにエラー検知と終了条件がある
- 下流スキルで必要なイベント（ローディング、エラー、画面遷移、空状態）が欠けていない

## 出力フォーマット

詳細テンプレートは `references/usecase_template.md` を参照する。

## アンチパターン

### ❌ 実装詳細を混ぜる

- `Repositoryのsave()を呼ぶ`
- `AsyncStreamをyieldする`
- `DBからSELECTする`

### ❌ 画面操作手順を本文に混ぜる

- `ユーザーは現在の問題の判定結果を入力する。（UI: 判定カードを右スワイプして正解、左スワイプして不正解を入力する）`

正しい書き方:

- `ユーザーは現在の問題の判定結果を入力する。`
- `## UIイベント`
- `- 基本フロー2「現在の問題の判定結果を入力する」: 判定カードを右スワイプして正解、左スワイプして不正解を入力する`

### ❌ 画面表示時の初期処理を書かない

- 画面遷移だけを書き、データ読み込みやローディング表示を省略する

### ❌ 1行に複数処理を書く

- `システムはローディング状態を非表示にし、履歴概要の一覧を表示する`
- 正しくは2手順に分割する（例: `ローディング状態を非表示にする` / `履歴概要の一覧を表示する`）

### ❌ 遷移直前の `保持する` を書く

- `システムは選択した学習回IDを保持する。`
- `システムは成績詳細画面へ遷移する。`
- 正しくは `システムは選択した学習回IDの成績詳細画面へ遷移する。`

### ❌ 分岐番号が元手順と一致しない

- 基本フロー3から分岐なのに `5-A` から始めない

### ❌ 主語を省略する

- `ローディング状態にする`
- `一覧画面へ戻る`

### ❌ 1ファイルに複数画面を混在させる

- `WordStudyScreen.md` に `ResultScreen` の操作を書く

### ❌ 画面構成を確定せずに書き始める

- 画面一覧が未確定のまま `docs/usecases` を作成する
